You are a senior full-stack engineer, AI engineer, and product architect. Build a complete functional prototype called “UdyamSetu”.

IMPORTANT CONTEXT:
UdyamSetu is an AI-assisted, rule-driven decision-support platform designed to help users understand and navigate financing/education-related schemes and reach the appropriate official next step.

This is NOT supposed to be a simple chatbot or a clickable UI mockup. The core journey must actually work end-to-end.

The fundamental principle of the application is:

AI understands and explains.
Deterministic rules and verified official data decide.

Do NOT allow an LLM to silently determine eligibility, invent scheme conditions, calculate financial values, invent partner information, or claim approval/sanction.

==================================================
1. CORE PRODUCT
==================================================

The main UdyamSetu journey is:

USER NEED
→ Understand Request
→ Structured User Profile
→ Rule-Based Eligibility
→ Scheme Matching + Explanation
→ Financial Understanding
→ Document Readiness
→ Authorized Partner Routing
→ Official Next Step

The user should be able to start with a need such as:

“I want ₹3 lakh for a dairy business.”

The application should collect/understand information such as:

- Purpose
- Project/business type
- Project cost
- Desired loan amount
- Income
- Education
- Location
- Relevant beneficiary/category information
- Other scheme-specific conditions

The user can provide information through forms and, where implemented, natural language/voice.

The system converts this into a structured profile.

The user MUST be shown the extracted/structured information and allowed to correct it before eligibility evaluation.

==================================================
5. RULE-BASED ELIGIBILITY ENGINE
==================================================

This is one of the most important parts of the application.

Implement eligibility as deterministic business rules.

The basic evaluation flow is:

STRUCTURED USER PROFILE
↓
Beneficiary/category eligible?
↓
Purpose/project eligible?
↓
Amount within scheme limit?
↓
Income/education/other conditions satisfied?
↓
ELIGIBLE / NOT ELIGIBLE
↓
Record explicit reasons

The engine should return structured results such as:

{
  "eligible": true,
  "scheme_id": "...",
  "reasons": [
    "...",
    "...",
    "..."
  ],
  "failed_conditions": []
}

For an ineligible scheme, explain exactly which rule failed.

Example:

NOT ELIGIBLE

Reason:
Requested loan amount ₹8,00,000 exceeds the maximum scheme limit of ₹5,00,000.

Do not return vague AI-generated explanations.

The rules should be auditable.

Each rule should ideally have:
- rule ID
- field
- operator
- expected value
- explanation
- source/version

==================================================
6. SCHEME MATCHING AND RANKING
==================================================

After evaluating eligibility, identify suitable schemes.

Ranking can consider:

- Loan/project amount fit
- Project/education compatibility
- Loan type
- Benefits/conditions
- Moratorium
- Repayment terms
- Suitable partner availability

Do NOT use fake AI percentages such as:

“95% match”

unless an actual validated scoring methodology exists.

Instead show:

“Why this scheme?”

Example:

Why this scheme?

✓ Your requested amount falls within the scheme limit.
✓ Your project type is supported.
✓ Your beneficiary category matches.
✓ The repayment terms are compatible.

The ranking logic should be deterministic and explainable.

==================================================
7. FINANCIAL CALCULATOR
==================================================

Build a deterministic financial calculation engine.

Input:

- Loan amount
- Interest rate
- Repayment period
- Moratorium
- Repayment frequency

Output:

- Estimated repayment/EMI where applicable
- Total interest
- Total repayment
- Plain-language explanation

IMPORTANT:

Financial calculations MUST NOT be generated by an LLM.

Use normal deterministic mathematical functions.

Separate:

OFFICIAL SCHEME PARAMETERS

from

CALCULATED ESTIMATES.

If a scheme does not use monthly repayment, do not falsely represent it as a monthly EMI scheme.

Display the official repayment frequency and terms.

Handle moratorium according to the scheme data.

The finance engine should be independently testable with unit tests.

==================================================
9. AI / NLP
==================================================

AI should be used as an assistance layer rather than the authority.

Possible responsibilities:

1. Natural-language understanding
2. Extract structured fields from user messages
3. Translation
4. Explanation
5. Grounded Q&A
6. Optional voice/STT processing

Example:

User:

“I need around three lakh rupees to start a dairy business. My annual income is around two lakh.”

AI/NLP extracts:

{
  "purpose": "business",
  "project_type": "dairy business",
  "requested_amount": 300000,
  "annual_income": 200000
}

Show this to the user:

“I understood:

Purpose: Business
Project: Dairy business
Requested amount: ₹3,00,000
Annual income: ₹2,00,000

Is this correct?”

Only after confirmation should the rules engine evaluate schemes.

AI MUST NOT:
- decide eligibility
- invent scheme rules
- invent interest rates
- calculate official repayment terms
- invent partners
- claim loan approval
- claim official verification

==================================================
10. RAG / GROUNDED Q&A
==================================================

Implement RAG only for answering questions about the curated scheme information.

Potential stack:

- Qdrant + embeddings

OR, if simplifying the MVP, use a vector-search solution compatible with the existing Supabase architecture.

The important requirement is that responses must be grounded in the curated official corpus.

Example:

User:
“What documents are required?”

The answer should come from the stored scheme data/source material.

Do not let the model freely hallucinate government scheme information.

Every important scheme explanation should expose its source.

12. PARTNER ROUTING
==================================================

Build an intelligent channel-partner router.

Input:

- User location
- Selected scheme

Routing flow:

USER LOCATION + SELECTED SCHEME
↓
Is partner authorized?
↓
Is partner compatible with scheme/category?
↓
Is operational status verified?
↓
Check fund-utilization/NPA information ONLY if official data exists
↓
Geospatial ranking
↓
Suitable authorized partners

The system should NOT simply select the nearest partner.

A nearby but incompatible partner should be excluded.

Example:

Partner A:
Distance: 2 km
Authorization: Verified
Scheme compatibility: No

→ EXCLUDE

Partner B:
Distance: 5 km
Authorization: Verified
Scheme compatibility: Yes

→ Suitable partner

Partner status rules:

Authorized + compatible + verified operational
→ Can rank normally

Verified unavailable
→ Do not route as active

Status unavailable
→ Do not infer
→ Display “Not verified — confirm”

Fund/NPA/overdue status unavailable
→ Do not infer
→ Display “Status not available”

DO NOT create a fake universal “partner approval limit”.

==================================================

Use:

- Service Worker
- IndexedDB
- Local caching
- Queued sync

Offline/low connectivity should support:

✓ Basic profile entry
✓ Core rule matching using cached rules
✓ Cached scheme information
✓ Financial calculation
✓ Document checklist
✓ Saved progress
✓ Queued actions

Connectivity is required for:

- Latest scheme updates
- Live partner status
- Live maps/directions
- Online AI/RAG
- Official online submission

Flow:

ONLINE
↓
Sync verified scheme/partner data
↓
LOCAL CACHE / INDEXEDDB
↓
CONNECTION DROPS
↓
Profile + matching + finance + checklist continue
↓
Pending actions queued
↓
CONNECTION RETURNS
↓
Sync + refresh official data + live functions

Show the user the freshness/version of cached information.

Do not build full offline maps for the MVP.
